# architecture.md - 技術仕様書

`docs/functional-design.md` で定義した論理設計を実現するための技術スタック・技術的制約・非機能要件の実現方針を定義する。個人利用・少数銘柄監視・Privateリポジトリという前提のもと、運用負荷が小さく単独開発でメンテナンスしやすい構成を優先する。

## 1. テクノロジースタック

### 1.1 全体構成

フロントエンドとバックエンドAPIを単一のNext.jsアプリケーションで実装するフルスタック構成とする。個人利用規模のため、インフラを複数サービスに分割せず運用負荷を最小化する。

| 分類 | 採用技術 | 選定理由 |
| --- | --- | --- |
| 言語 | TypeScript | フロント/バック共通言語で型安全性を確保 |
| フレームワーク | Next.js (App Router) | フロントエンドとAPI Routesを1リポジトリで完結できる |
| UIライブラリ | React + Tailwind CSS | レスポンシブUIを効率的に実装 |
| ORM | Prisma | スキーマ駆動でデータモデルとマイグレーションを管理 |
| データベース | PostgreSQL(本番) / SQLite(ローカル開発) | 個人利用規模で十分。Prisma経由で切替容易 |
| 非同期処理 | サーバーアクション/APIルート内の非同期実行 + ジョブステータス管理 | 追加のキュー基盤(Redis等)を持たず調査処理の実行状態をDBで管理し、運用負荷を抑える |
| 外部検索連携 | Web検索API・YouTube Data API・SNS APIをアダプタ経由で呼び出し | プロバイダ差し替え・キー未設定時のモック動作を可能にする |
| テスト | Vitest(ユニット) / Playwright(E2E最小限) | フロント・バック双方をカバー |
| Lint/Format | ESLint + Prettier | コーディング規約の機械的担保 |

### 1.2 モジュール構成方針

- `src/app/` : Next.js App Router によるページ・レイアウト
- `src/features/` : 機能単位(watchlist, investigation, market-data)でUI・サーバー処理をまとめる
- `src/lib/search-providers/` : Web/YouTube/SNS検索のアダプタ実装(プロバイダ差し替え可能なインターフェース)
- `src/lib/signal-extraction/` : 検索結果からシグナル(数量/単価の増減)を抽出するロジック
- `prisma/` : スキーマ定義・マイグレーション

## 2. 開発ツールと手法

- パッケージ管理: npm
- バージョン管理: Git / GitHubのPrivateリポジトリ
- ブランチ運用: `main` を安定ブランチとし、作業は `.steering/` の作業単位ごとにブランチを切って `main` へマージする
- CI: GitHub Actionsでlint・typecheck・testを実行(将来追加、初期実装では手動実行から開始してもよい)
- 環境変数管理: `.env.local`(ローカル)、デプロイ先のシークレットマネージャ(本番)。`.env.example` にキー名一覧のみをコミットし、値はコミットしない

## 3. 技術的制約と要件

- 証券会社APIの認証情報・取得済みデータの連携方式は既存の取得済みデータ(バッチ等で取り込まれたデータ)を読み込む前提とし、本アプリから証券会社APIへ直接発行するリクエストの実装は初期スコープに含めない。データ取り込み用のインポート機構(CSV/JSON取り込み等)を用意する。
- Web検索API・YouTube Data API・SNS APIは、それぞれ利用規約・レート制限が存在するため、以下を満たすこと。
  - APIキー未設定の場合はモックプロバイダで動作し、開発・検証を妨げないこと
  - 呼び出し頻度はユーザーが調査を明示的に実行した時のみとし、定期バッチでの大量呼び出しは行わない
  - SNS APIは提供元の仕様変更・利用制限が大きいため、初期実装ではアダプタのインターフェースのみ定義し、実装は段階的に追加してよい
- Privateリポジトリ運用を前提とし、APIキー等の秘匿情報はコード・リポジトリに含めない(環境変数経由)

## 4. パフォーマンス要件

- 銘柄詳細画面の初期表示(株価・財務データ・直近シグナル要約)は3秒以内を目安とする
- 調査実行(Web/YouTube/SNS検索〜シグナル判定)は非同期処理とし、画面をブロックしない。処理中はステータス表示を行う
- 監視銘柄数は数社〜十数社程度を想定した設計とし、大規模同時アクセスは考慮しない(個人利用のため)

## 5. デプロイ構成(概要)

- ホスティング: Vercel等のNext.js対応ホスティング、またはDocker化してのセルフホストのいずれかを想定(初期実装ではローカル開発環境での動作を優先し、デプロイ先は実装後に確定してもよい)
- データベース: マネージドPostgreSQL(例: Supabase, Neon等)を想定
